# Ulfberht — pandoc, make, and nothing else

A static site with no framework, no `node_modules`, and no build config
longer than the content. Two boring old tools do everything: **pandoc**
turns markdown into pages, **make** decides what needs rebuilding.
Named after the Ulfberht blade — purist, efficient, no compromise on
quality.

- **Live demo:** <https://erdivartanovich.github.io/>
- **The story, as a writing:**
  [Building this site: pandoc, make, and nothing else](https://erdivartanovich.github.io/writings/building-this-site.html)

## What you need

- `pandoc`
- `make` (GNU make)
- a POSIX shell (`sh` — dash, bash, zsh all work)

That's it. No npm, no runtime, no lockfile. For the GitHub Pages
workflow, all you need is a repository named `[username].github.io` —
no separate "site" to create. See
[Creating a GitHub Pages site](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site)
for the full details.

## Project layout

```
.
├── Makefile                 # the whole build (~45 lines)
├── site.yaml                # site-wide metadata: title, url, nav, css
├── pages/                   # markdown sources
│   ├── index.md             # homepage
│   ├── about.md             # static page (no date: → not a post)
│   ├── portfolio.md         # static page
│   ├── writings.md          # writings index; shows the post list
│   ├── 404.md               # not-found page
│   └── writings/            # posts live here
├── templates/
│   └── main.html            # pandoc template: $title$, $date$, $body$, …
├── scripts/
│   ├── gen-writings.sh      # scrapes posts → writings.yaml (newest first)
│   ├── gen-feed.sh          # Atom feed (feed.xml)
│   └── gen-sitemap.sh       # sitemap.xml (index → /, 404 excluded)
├── assets/                  # css, images, favicon, robots.txt
├── dist/                    # build output — generated, gitignored
└── writings.yaml            # generated by gen-writings.sh — gitignored
```

## Quick start

```sh
make                         # build everything into dist/
cd dist && python3 -m http.server  # preview locally
```

`make` produces pages, copies assets, and regenerates the writings list,
the Atom feed, the sitemap, and redirect stubs for old URLs.

## How it works

One convention drives the whole site: **a page with a `date:` in its
frontmatter is a writing.** Everything else derives from that fact.

A writing gets:

- a **table of contents** (from `--toc`)
- an entry in `writings.yaml` → the homepage and `/writings.html` list
- an **Atom feed** entry in `feed.xml`
- a `lastmod` entry in `sitemap.xml`

### The build rule

A single make pattern rule handles every page — write it once, make
generates it for every file:

```make
$(OUT)/%.html: pages/%.md $(TEMPLATE) $(SITEMETA) $(WRITINGS_META)
	@mkdir -p $(@D)
	$(PANDOC) $< --template $(TEMPLATE) --standalone \
	  --highlight-style=monochrome \
	  $$(awk '/^---$$/{n++; if(n==2) exit} /^date:/{print "--toc --toc-depth=3"; exit}' $<) \
	  --metadata-file=$(SITEMETA) --metadata-file=$(WRITINGS_META) -o $@
```

Read it like a sentence: `page.html` depends on `page.md`, the
template, and both YAML files. If any dependency is newer than the
output, make re-runs the recipe. Touch the template and every page
rebuilds; touch one post and only that page rebuilds.

The `awk` bit is the frontmatter probe: if the page has a `date:`, it's
a writing, so pandoc gets `--toc --toc-depth=3`.

### The template

`templates/main.html` is a pandoc template — one HTML shell with slots:

- `$title$`, `$author$`, `$date$` — page metadata
- `$body$` — the converted markdown
- `$for(writings)$` — loops the post list (fed from `writings.yaml`)
- `$for(navigation)$` — the nav links (fed from `site.yaml`)

Site-wide settings live in `site.yaml`: title, URL, CSS, and the nav.
Change a nav link once; every page picks it up on the next build.

### The scripts

Three POSIX-sh scripts parse frontmatter with `awk` — no dependencies:

- `gen-writings.sh` — scrapes `title`/`date` from every page under
  `pages/writings/`, sorts newest-first, writes `writings.yaml`.
- `gen-feed.sh` — writes the Atom feed from the same frontmatter.
- `gen-sitemap.sh` — lists every page; maps `index.md` to `/` and skips
  `404.md`. `lastmod` comes from git (`git log -1 --format=%cs`), falling
  back to `date:` outside a repo — the CI checkout must use
  `fetch-depth: 0` so lastmod is real, not the publish date.

## Writing a post

1. Create `pages/writings/your-post.md` with frontmatter:

   ```markdown
   ---
   title: "Your post title"
   author: "Your Name"
   date: "2026-08-05"
   description: "One line for SEO, the feed, and the og: tag."
   modified: "2026-08-05"   # optional: set when you edit an existing post
   related:                  # optional: internal links, shown on the post
     - url: /writings/other-post.html
       title: "Other post title"
   ---

   Write your post in markdown.
   ```

   `modified:` feeds `article:modified_time` and the JSON-LD `dateModified`;
   `related:` renders a "Related" block for crawl + dwell-time signals.
   The sitemap `lastmod` is taken from git history (see below), not
   `date:` — so an edit needs no frontmatter bump, just a commit.

2. Run `make`. The homepage, the writings page, the feed, and the
   sitemap all update themselves — no list to maintain by hand.
3. Preview locally, then push. Deploying is copying `dist/`.

## Customizing

- **Nav, site name, URL** — `site.yaml`.
- **Layout, header, footer** — `templates/main.html`.
- **Colors and fonts** — `assets/theme.css` (color variables) and
  `assets/styles.css` (layout).
- **Writings list placement** — set `show-writings: true` in a page's
  frontmatter to render the post list inside that page.

## Deploying

The build output is a folder of static HTML files. No server runtime,
no adapter, no lock-in — anywhere that serves files works. The repo
ships with a GitHub Pages workflow; the same `dist/` folder drops into
Firebase, Cloudflare, or your own box just as easily.

### GitHub Pages (what this repo uses)

`.github/workflows/deploy.yml` does the whole job: installs pandoc via
`apt`, runs `make`, and publishes `dist/` with the official
`actions/deploy-pages` workflow.

To use it: push to `main`, and enable **Settings → Pages → Deploy from
a workflow** (Build and Deployment → GitHub Actions). No other config.

### Firebase Hosting

```sh
npm install -g firebase-tools
firebase init hosting   # public dir: dist
firebase deploy
```

The free Spark plan is plenty for a personal blog.

### Cloudflare Pages

```sh
npm install -g wrangler
make
wrangler pages deploy dist
```

Free tier, generous bandwidth, instant cache invalidation.

### Your own server + nginx/Caddy

```sh
make
rsync -av dist/ user@server:/var/www/ulfberht/
```

Then let a gateway serve that directory. Caddy's whole config is two
lines, TLS included:

```caddyfile
example.com {
    root * /var/www/ulfberht
    file_server
}
```

nginx needs a few lines and a certificate, same idea. Because there is
no app server, the gateway is pure static serving — the simplest front
door a site can have.

## Editor tips

Because the whole machine is one Makefile, your editor is the dev
server.

- **Vim/Neovim:** `:make` rebuilds and puts errors in the quickfix list
  (`:copen`, `:cn` to navigate).
- **Emacs:** `M-x compile`, then `M-x recompile`.
- **Literal hot reload** (Linux, needs `inotify-tools`):

  ```sh
  while inotifywait -q -r -e close_write pages; do make; done
  ```

## FAQ

**Why no tags, search, or pagination?**
A personal blog is mostly words. Those features are DIY here — that's
the honest trade for zero dependencies.

**What breaks first at scale?**
The flat file layout. A few hundred posts would want subfolders and
pagination.

**Can I write posts in org-mode instead of markdown?**
Mostly — pandoc reads org files natively. The post list is scraped from
YAML frontmatter, so an org post still needs a `date:` header.

**Why are there stub files for old URLs?**
The `MOVED` list in the Makefile writes meta-refresh stubs so old flat
URLs (like `/bash-without-if.html`) and the pre-rename `/articles/...`
URLs all redirect to `/writings/...`.
